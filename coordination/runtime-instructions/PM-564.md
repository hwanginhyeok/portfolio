# Build a daily Wanted (원티드) job-posting collector for the portfolio project

Project root: /home/window11/포트폴리오 (Astro site + job-application docs).
Goal: a cron-ready Python collector that pulls matching job postings from Wanted
into a staging inbox, so the owner can map them onto existing portfolio cases.

## Verified API facts — I probed these live on 2026-08-18. Do NOT re-derive them, do NOT invent other endpoints, do NOT use a headless browser. Plain HTTP with `requests` is enough; no auth, no cookies.

### 1. Keyword search
GET https://www.wanted.co.kr/api/chaos/search/v1/results
  query params: query=<keyword>&tab=position&limit=<n>&offset=<n>
  headers: User-Agent = a desktop Chrome UA string; Referer = https://www.wanted.co.kr/search
  response JSON: {"positions": {"data": [ {...} ], "total_count": N}, "companies": {...}}
  each positions.data item: {"id": int, "position": str, "company": {"id": int, "name": str}, "address": {...}}
  Measured today: query="프로젝트 매니저" total=44 · "제조 AI" total=8 · "생산관리" total=12 ·
  "AI 엔지니어" total=128 · "PM" total=800 (very noisy — matches 서비스기획/사업개발).

### 2. Posting detail (full JD text)
GET https://www.wanted.co.kr/api/v4/jobs/{id}
  headers: same User-Agent
  response JSON: {"job": {"id", "status", "due_time", "skill_tags": [...], "address": {...},
    "company": {...}, "detail": {"position", "intro", "main_tasks", "requirements",
    "preferred_points", "benefits", "hire_rounds"}}}
  The `detail` fields hold the complete JD body text. This is the payload that matters.
  Alternative endpoint https://www.wanted.co.kr/api/chaos/jobs/v4/{id}/details returns the
  same detail fields nested under {"data": {"job": {...}}}. Use /api/v4/jobs/{id} first and
  fall back to the chaos one only on a non-200.

### 3. Company lookup (for the watchlist)
Same search endpoint with tab=all:
  response.companies.data items: {"id", "name", "confirmed_position_count", "industry_name"}
  Measured today: 현대자동차 → 0 · 현대자동차(남양연구소) → 0 · 현대모비스 → 0 ·
  삼성전자 → 0 · 삼성전자서비스 → 0 · SK하이닉스 → no company entry at all.
  ZERO IS THE EXPECTED VALUE. These conglomerates recruit through their own portals.
  The watchlist exists precisely to catch the day one of them becomes non-zero.
  Do not treat a 0 as a bug, and do not try to work around it by scraping other sites.

## Deliverables (exactly these files, nothing else)

### A. `config/wanted_targets.json` (new directory `config/`)
```json
{
  "keywords": ["제조 AI", "프로젝트 매니저", "자율제조", "생산관리", "AI 엔지니어",
               "Product Manager", "기술 PM", "PMO", "스마트팩토리"],
  "company_watchlist": ["현대자동차", "현대자동차(남양연구소)", "현대모비스", "현대오토에버",
                        "기아", "삼성전자", "SK하이닉스", "SK", "LG전자"],
  "exclude_title_patterns": ["인턴", "계약직", "아르바이트"],
  "per_keyword_cap": 100,
  "request_delay_seconds": 1.0
}
```
Tune the lists if a measured run shows a keyword returns pure noise — but say so in the
report and keep the edit in this file, never hardcoded in the script.

### B. `scripts/wanted_collect.py`
- stdlib + `requests` only (confirmed installed). No new dependencies.
- CLI: `python3 scripts/wanted_collect.py [--config PATH] [--dry-run] [--limit N]`
  - `--dry-run` fetches and prints a summary but writes NO files
  - `--limit N` caps detail fetches for a quick smoke test
- Flow: for each keyword, page the search endpoint (offset += limit) up to `per_keyword_cap`
  → union results by job `id` → drop ids already in state → drop titles matching
  `exclude_title_patterns` → fetch detail for each remaining id → write one markdown file.
- Politeness: single-threaded, `time.sleep(request_delay_seconds)` between every HTTP call.
- Resilience: a non-200 on one item is logged and skipped, never fatal. Exit non-zero only
  if every keyword's search failed (i.e. the API is down or shape-changed).
- Watchlist: for each `company_watchlist` name, run the tab=all search and record the matched
  company's `confirmed_position_count`. Match on exact name where possible.

### C. State + output under `docs/jd/_inbox/wanted/`
- `state.json` — `{"seen": {"<id>": {"first_seen": "YYYY-MM-DD", "company": str, "position": str}}}`
  This is the dedup ledger. Re-running the same day must produce zero new files.
- `<id>-<company-slug>.md` per posting — YAML frontmatter
  (`wanted_id`, `company`, `position`, `url` = https://www.wanted.co.kr/wd/<id>, `location`,
  `skill_tags`, `due_time`, `first_seen`, `matched_keywords`) followed by the JD sections
  (소개 / 주요업무 / 자격요건 / 우대사항 / 혜택 / 채용절차) rendered from the `detail` fields.
  Omit a section when its field is empty rather than printing an empty heading.
- `digest/YYYY-MM-DD.md` — the daily report. Top of file: the watchlist status line
  (company → position count), with any NON-ZERO watchlist company called out loudly at the
  very top. Then a table of the postings newly seen that day (회사 | 포지션 | 지역 | 링크).
  If nothing is new, still write the digest saying so, including the watchlist line.
- `README.md` — what this inbox is, how to run it, and its relation to the existing rule in
  `docs/jd/README.md` 원칙 1 (회사별 디렉토리 완전 분리): this inbox is a STAGING area only.
  Promoting a posting to a real application means creating `docs/jd/{회사}/` per that rule
  and copying what is needed; the inbox is never the SSOT for an active application.
