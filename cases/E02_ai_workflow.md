# Case Study: AI를 프로세스에 통합하다 — Claude Code 기반 엔지니어링 자동화

> "AI를 사용하는 수준"이 아니라 "AI 워크플로우를 설계하는 수준"
> 도구: Claude Code (Anthropic CLI)
> 적용 영역: 이슈 관리 / 주간보고 / 기술 분석 / 프로젝트 통합 모니터링

---

## 한 줄 요약

Claude Code를 단순 코딩 보조가 아니라, **개발 프로세스 자체에 통합**해서 사용. 5개 에이전트 시스템 설계, 8개 프로젝트 통합 모니터링, 이슈/주간보고/시황 자동화까지 — "AI를 운영"하는 수준의 워크플로우.

---

## 시작점 — 왜 AI 워크플로우 설계인가

엔지니어 1명이 다음을 동시에 운영해야 했습니다:

- **본업 1**: SS500 모터제어 개발 (CAN, 배터리, 안전 시스템)
- **본업 2**: PM 겸임 (이슈 트래킹, BOM, 글로벌 협업)
- **사이드**: 자율주행 / 정치통계 / 주식분석 / 음악AI 등 8개 프로젝트 (E03 참조)

AI를 "코드 짜주는 비서"로 쓰면 도움은 되지만 한계가 명확합니다. 그래서 **운영 프로세스 자체를 AI가 굴리도록** 설계하기 시작했습니다.

---

## 1. 5개 에이전트 시스템 (HIH 프로젝트)

SS500 프로젝트 운영을 위해 5개 역할 에이전트를 설계했습니다.

| 에이전트 | 역할 | 도구 |
|---------|------|------|
| **PM_Lead** | 이슈 우선순위, 일정, 의사결정 게이트 | Notion API, 캘린더, 이슈 DB |
| **Engineer_1** | 모터제어 / CAN / 배터리 분석 | Python, CAN 로그 파서, 데이터 시각화 |
| **Engineer_2** | 펌웨어 / VCU / 상태머신 | C/C++, STM32 툴체인 |
| **Engineer_3** | 시험 / 검증 / 데이터 분석 | 다이나모 데이터, 엑셀 자동화 |
| **Notion_Admin** | 문서 동기화, INDEX 자동 생성 | Notion MCP, 마크다운 변환 |

### 작동 방식

```
이슈 발견 (CAN 로그 / 시험 결과)
  ↓
Engineer_1 또는 _3 분석
  ↓
PM_Lead가 우선순위 / 의사결정
  ↓
Notion_Admin이 DB 등록 / 마크다운 동기화
  ↓
주간 회의에서 사람이 최종 판단
```

→ **반복 작업은 AI가, 판단은 사람이**.

---

## 2. 프로젝트관리자(PM) 시스템 — 8개 프로젝트 통합 모니터링

8개 프로젝트의 git 현황, 태스크, 디스크, 백업을 **하나의 CLI + cron**으로 통합 관리하는 시스템.

### 구조

```
project-manager/
├── projects.yaml          ← 8개 프로젝트 레지스트리 (SSOT)
├── pm.py                  ← 통합 CLI
├── daily_report.py        ← 07:00 cron
├── weekly_report.py       ← 일요일 22:00 cron
├── overnight_runner.py    ← 00:00 cron (야간작업 자동 실행)
└── docs/
    └── projects/          ← 각 프로젝트 심링크 (TASK, CLAUDE, DIFFICULTY)
```

### 핵심 명령어

| 명령 | 기능 |
|------|------|
| `pm.py status` | 8개 프로젝트 git 상태 + 태스크 현황 한눈에 |
| `pm.py morning` | 09:00 아침 브리핑 |
| `pm.py tonight` | 야간작업 프롬프트 자동 생성 |
| `pm.py validate` | 설정 + 태스크 + 심링크 검증 |
| `daily_report.py` | 일간 리포트 → JSON |
| `overnight_runner.py` | tonight_prompt.txt 읽고 야간 자동 작업 |

### 운영 원칙

- **PM은 오케스트레이터**: 직접 수정 안 함. 각 프로젝트 세션에 tmux로 지시만 전달.
- **SSOT 원칙**: 정보는 한 곳에만. 나머지는 심링크. AI 환각 방지.
- **읽기 전용**: PM 세션은 읽기만. 수정은 각 프로젝트 세션에서.

## 3. 야간작업 자동화 — Overnight Runner

```
00:00 cron 발동
  ↓
overnight_runner.py가 tonight_prompt.txt 읽기
  ↓
8개 프로젝트 중 야간작업 지정된 항목 순차 실행
  ↓
각 항목 완료마다 git 커밋 (작은 단위)
  ↓
완료 시 docs/프로젝트/overnight_brief_YYYYMMDD.md 생성
  ↓
07:00 daily_report에서 야간작업 결과 포함
```

**금지 사항** (야간작업 룰):
- `git push` 금지 (사용자 검토 후 수동 push)
- `rm -rf` 금지
- `.env` / credentials 수정 금지
- DB DDL 변경 금지

→ "AI가 자동으로 일하지만, 위험한 일은 사람이 한다"는 원칙.

## 4. 시황/콘텐츠 자동화 — x-bot, music-lab, my-politics-stats

| 프로젝트 | 자동화 영역 | 주기 |
|---------|------------|------|
| x-bot | 주식 시황 브리핑 (네이버 글) | 매일 06:00, 18:00 |
| music-lab | Suno AI 곡 생성 → 로컬 저장 | 사용자 트리거 |
| my-politics-stats | 카드뉴스 draft 생성 | 사용자 트리거 |
| insung_blog | 블로그 댓글 자동 응답 | 24시간 |

**게시 승인 게이트** (publish-gate 룰):
- 자동 생성은 OK
- **자동 게시는 금지** — 사용자 승인 후만 외부 게시
- `draft → pending_review → approved → published` 상태 흐름

## 5. 기술 분석 페어링 — Claude와 함께 CAN 로그 분석

**일반 사용**: "이 CAN 로그 분석해줘" → AI가 한 번 분석 → 끝

**본인 사용**:

```
1. CAN 로그 + DBC 파일 + 기대값 시트를 컨텍스트로 제공
2. AI에게 "신호별 정합성 검증" 작업 지시
3. AI가 정량적 비교표 생성 → 본인이 검토
4. 이상 신호 발견 시 → AI에게 "왜 이 신호가 162%까지 올라가는지 추정해줘"
5. AI 추정 + 본인 도메인 지식 결합 → 실제 검증 시험 설계
6. 시험 결과 → AI에게 다시 입력 → 다음 가설
```

→ **단발성 질문**이 아닌 **루프**. AI는 도메인 지식 빠른 액세스 + 시각화 + 정량화 도구.

## 6. 글로벌 룰 시스템 — AI에게 원칙을 가르치기

`global-rules/` 디렉토리에 11개 규칙 파일을 두고, 모든 Claude Code 세션 시작 시 자동 로드.

| 룰 | 내용 |
|----|------|
| `ssot.md` | Single Source of Truth + 심링크 원칙 |
| `task-management.md` | 태스크 3단계 (Current/Prepared/Finished) |
| `publish-gate.md` | 게시 승인 게이트 |
| `doc-size.md` | md 파일 300~500줄 제한 |
| `test-first.md` | 선검증 후도입 |
| `cron.md` | cron 종합 관리 |
| `overnight.md` | 야간작업 규칙 |
| `deep-fp.md` | 제1원칙 + 5단계 사고 |
| `deep-ontology.md` | 온톨로지적 사고 |
| `llm-architecture.md` | Head/Worker/Drone 3계층 |
| `model-routing.md` | 모델별 작업 분배 정책 |

→ AI에게 **개별 작업이 아닌 운영 원칙**을 가르침. 결과적으로 매번 같은 지시 반복할 필요가 없어짐.

## 정량적 성과

| 항목 | Before (AI 통합 전) | After |
|------|--------------------|-------|
| 8개 프로젝트 상태 파악 | 각각 디렉토리 들어가서 확인 | `pm.py status` 1초 |
| 주간보고 작성 | 수동 작성 1~2시간 | `weekly_report.py` 자동 |
| 야간작업 | 다음날 수동 진행 | overnight_runner 자동 + git 커밋 |
| 이슈 관리 | Notion 수동 동기화 | Notion_Admin 에이전트 자동 |
| 시황 브리핑 | 매일 수동 작성 | x-bot 자동 발행 |
| CAN 로그 분석 | 엑셀 수작업 | AI 페어 분석 + 정량화 |

→ 엔지니어 1명이 **8개 프로젝트 + 본업 + PM**을 동시에 굴릴 수 있게 된 핵심 인프라.

## 이 케이스가 보여주는 역량

| 역량 | 근거 |
|------|------|
| **AI 워크플로우 설계** | 5개 에이전트, 11개 글로벌 룰, 8개 프로젝트 통합 |
| **시스템 사고** | 단발 자동화가 아닌 SSOT/심링크/cron 통합 운영 |
| **자동화 한계 인식** | 게시 승인 게이트, 야간작업 금지 사항 — "어디까지 자동화할지" 설계 |
| **도구 통합** | Claude Code + Notion API + cron + tmux + git |
| **운영 효율화** | 1명이 8개 프로젝트 + 본업 동시 운영 |
| **AI 페어 엔지니어링** | CAN 로그 분석, 배터리 정합성을 AI와 페어로 |

## 면접 예상 Q&A

**Q: 회사 업무에 개인 AI 도구를 쓰는 건 보안 문제 없나요?**

> 사내 정책에 따라 회사 데이터는 사내 시스템에서, 사이드/개인 프로젝트는 개인 환경에서 분리해서 사용합니다. AI 워크플로우 **설계 역량 자체**가 회사에 가치 있는 자산이지, 데이터를 외부로 보낸다는 의미는 아닙니다.

**Q: AI가 만든 결과물의 신뢰성은 어떻게 검증하나요?**

> 두 가지 원칙입니다.
> 1. **글로벌 룰 `test-first.md`**: AI가 만든 결과는 **별도 검증** 후 도입. 수정 → 결과 → 사용자 승인 → 적용.
> 2. **정량적 검증**: AI 분석은 항상 정량 데이터(CAN 로그, 측정값)와 대조. 도메인 지식이 없는 사람에게 의존하지 않습니다.

**Q: AI 없이도 일할 수 있나요?**

> 네. AI가 굴리는 워크플로우는 모두 **사람이 운영하던 프로세스를 자동화**한 것입니다. AI가 사라져도 워크플로우 자체는 살아있고, 다시 사람이 굴리면 됩니다. AI는 **속도와 빈도의 도구**이지, 본질을 만드는 도구는 아닙니다.
