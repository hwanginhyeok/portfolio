# Engineering Philosophy — 일하는 방식의 원칙

> "내 언어의 한계가 내 세계의 한계다" — 비트겐슈타인
> "삭제한 것 중 10%를 다시 추가하지 않는다면, 충분히 삭제 안 한 것이다" — 일론 머스크

---

## 한 줄 요약

7개의 짧은 원칙으로 일합니다. 각 원칙은 **실패 경험 또는 검증된 사례**에서 나왔고, 케이스 D1~D12 / E01~E03에 흔적이 남아 있습니다.

---

## 원칙 1. 측정할 수 없으면 개선할 수 없다

**출처**: 피터 드러커 / D12 시험 주도 엔지니어 케이스

**의미**: 엔지니어링에서 가장 위험한 말은 "대충 될 것 같다". 시험 방법이 없으면 만든다. 데이터가 없으면 만든다. **감으로 하지 않는다**.

**실증**:
- 다이나모미터 토크 측정 시스템 직접 설계 (비선형성 0.008%, D12)
- SVPWM vs DPWM 온도 차이를 16°C로 정량화 (D12)
- SOC 162.4% 오버플로우를 CAN 로그에서 발견 (D2)

---

## 원칙 2. 제1원칙에서 출발한다

**출처**: 일론 머스크 / `global-rules/deep-fp.md`

**의미**: 유추적 사고("남들이 이렇게 하니까")가 아니라 제1원칙 사고("물리적으로 참인 것은?")에서 출발한다.

```
1. 가정 나열 → 당연하게 여기는 것은?
2. 가정 깨기 → 정말 사실인가? 증거는?
3. 근본 진실 → 절대적으로 참인 것만 남기면?
4. 재구성    → 근본 진실만으로 새 솔루션
5. 검증      → 실패하면 1로
```

**실증**:
- "농기계는 농기계다" 가정을 깨고 "Physical AI 제품이다"로 재정의 (D1)
- "배터리 업체가 ROM 수정했다고 하면 됐다" 가정을 깨고 매번 검증 (D2)
- 펌프 파워 부족을 받아들이지 않고 0.96kW → 3.23kW 전력 예산 분석 (D4)

## 원칙 3. 머스크의 5단계를 순서대로 따른다

**출처**: `global-rules/deep-fp.md`

```
1. 요구사항을 의문시하라  ← 가장 먼저
2. 삭제하라              ← 두 번째
3. 단순화/최적화하라      ← 세 번째
4. 속도를 높여라          ← 네 번째
5. 자동화하라            ← 가장 마지막
```

**의미**: 순서를 어기면 잘못된 것을 빠르게 자동화하게 된다. **존재해서는 안 되는 것을 최적화하는 것보다 바보 같은 일은 없다**.

**실증**:
- SS500 상태머신에서 NONE 상태를 "삭제" → 안전 버그 자동 해결 (D3)
- AI 워크플로우 설계 시 자동화는 가장 마지막 — 글로벌 룰 / SSOT 정립이 먼저 (E02)

---

## 원칙 4. 온톨로지로 문제를 구조화한다

**출처**: 아리스토텔레스 / `global-rules/deep-ontology.md`

**의미**: 문제를 만나면 "이 문제의 세계에는 무엇이 존재하는가?"를 먼저 묻는다. 코드를 쓰기 전에 **개체 / 속성 / 관계 / 제약 / 계층**을 정의하면 모호함이 구조로 바뀐다.

```
1. 개체 식별  → 어떤 사물/개념/행위자가 존재하는가?
2. 속성 정의  → 각 개체는 어떤 특성?
3. 관계 매핑  → 어떻게 연결? (is-a, has-a, causes)
4. 제약조건   → 어떤 조합이 불가능한가?
5. 계층 구조  → 상위/하위 범주는?
```

**실증**:
- SS500 상태머신: RC / LCD / ADT 3모드를 개체로, "제어권 보유" 상태를 속성으로, 전환을 관계로 정의 → 안전 설계 명확화 (D3)
- 프로젝트관리자: 8개 프로젝트를 개체로, projects.yaml에 속성/관계/제약을 정의 → 통합 모니터링 가능 (E02)

---

## 원칙 5. 선검증 후도입 (test-first)

**출처**: `global-rules/test-first.md`

**의미**: 코드 변경 / 기능 추가 시 **먼저 검증하고, 결과를 보고한 후, 사용자 승인을 받아 도입**한다.

```
1. 조사/분석   → 현재 상태 + 영향 범위
2. 검증       → 별도 테스트 (dry-run, 샌드박스)
3. 상황 보고  → 검증 결과 + 리스크
4. 승인       → 사용자 확인
5. 도입       → 실제 코드 적용
```

**금지 패턴**:
- "이렇게 하자 → 수정 → 안 됨" 반복
- "아마 될 겁니다" → 에러 → 재수정
- 프로덕션에서 시행착오

**실증**:
- 배터리 ROM 업데이트마다 별도 검증 사이클 (D2)
- 야간작업 자동화에서도 git push는 사람이 (E02)

---

## 원칙 6. SSOT — 정보는 한 곳에만

**출처**: `global-rules/ssot.md`

**의미**: 같은 정보를 두 곳에 쓰지 않는다. 나머지는 심링크 또는 참조. AI가 중복/상충 정보를 보면 환각을 일으키고, 사람도 어느 게 진실인지 모른다.

**실증**:
- 8개 프로젝트의 TASK / CLAUDE / DIFFICULTY가 PM 시스템에 심링크로 연결 (E02)
- BOM V0.3.4가 단일 진실의 원천 — 132개 부품 (E01)
- CAN DBC가 4종, 각각의 정본이 명확 (D1)

---

## 원칙 7. 책임 라인을 분리한다

**출처**: `global-rules/publish-gate.md` / 야간작업 룰

**의미**: 자동화는 효율을 높이지만, **책임은 사람이 진다**. 자동 생성은 OK, 자동 게시는 금지. 자동 작업은 OK, git push는 사람이.

```
draft → pending_review → approved → published
```

**실증**:
- 정치통계 카드뉴스: AI가 만들지만 사용자 승인 후 발행 (E03)
- 음악AI: Suno로 곡 생성하지만 YouTube 업로드는 사용자 지시 후 (E03)
- 야간작업: AI가 코드 짜지만 git push는 사용자가 (E02)

---

## 원칙 8. 기술 깊이와 제품 감각을 동시에

**출처**: D1 커리어 내러티브

**의미**: "기술만 잘하는 엔지니어"도 "PM만 잘하는 매니저"도 아닌, **둘을 동시에 갖춘 브릿지 엔지니어**가 되려고 한다.

**실증**:
- SS500에서 모터제어 본업 + PM 겸임 (D1, E01)
- 배터리 업체 협의에서 기술 + PM 판단 동시 수행 (D2)
- "전달자 PM"이 아닌 "판단자 PM"으로 의사결정 사이클 단축 (E01)

## 종합 — 이 원칙들이 만드는 것

```
온톨로지로 구조화 → 제1원칙으로 근본 발견 → 5단계로 실행
        ↓                                          ↓
   문제의 세계를 본다                         삭제 / 단순화 / 자동화
        ↓                                          ↓
   SSOT로 정보 정리                          선검증 후도입
        ↓                                          ↓
   측정 가능한 시스템 ← ─ ─ ─ 책임 라인 분리
```

**결과**:
- 같은 시간에 더 많은 일 (E02 8개 프로젝트 동시 운영)
- 같은 일에 더 깊은 검증 (D2 SOC 162% 발견)
- 실패가 누적되어도 빠르게 복구 (D12 9개 시험 체계)

---

## 한 문장으로

> **"근본을 보고, 삭제로 시작하고, 측정으로 끝낸다. 책임은 분리하지 않고, 도메인은 분리하지 않는다."**

## 면접 예상 Q&A

**Q: 원칙이 너무 많지 않나요?**

> 7개로 보이지만 본질은 하나입니다 — **"근본을 보고, 측정한다"**. 나머지 원칙(5단계, 온톨로지, 선검증)은 그 본질을 실제 작업에서 운영하는 도구일 뿐입니다.

**Q: 이론적인 거 아닌가요?**

> 각 원칙마다 실제 사례(D2/D3/D4/D12/E01~E03)를 1대1로 매핑합니다. 원칙이 케이스보다 먼저 있었던 것이 아니라, **케이스에서 패턴이 발견되어 원칙이 된 것**입니다.

**Q: 가장 중요한 원칙 하나만?**

> **원칙 1: 측정할 수 없으면 개선할 수 없다**. 나머지 모든 원칙이 이 한 줄을 다른 각도에서 말하고 있습니다.
