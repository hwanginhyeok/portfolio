## 6. Track A — DFMEA로 본 현장 (홈 임팩트 섹션 #1)

### 6.1 섹션 타이틀
**DFMEA로 본 현장 — 고장모드에서 설계로 돌아간다**

> DFMEA는 문서가 아니다. 고장모드를 먼저 상상하고, 설계로 돌아가는 사고방식이다.
> 현장에서 사고가 나기 전에 Boundary Diagram에서 그 고장을 잡는다.

### 6.2 공통 프레임 (카드마다 4줄 고정)
1. **고장모드** (FM 번호)
2. **근본원인** (RCA)
3. **설계 변경** (대책)
4. **검증** (재현 시험 / 데이터)

### 6.3 에피소드 4건

#### A-1. MCB 접점 탄화 — 48V 전력단자 전해부식
- **고장모드**: D-13 (48V 전력단자 부식) · Issue #204
- **근본원인**: 전해 부식 → 접촉저항↑ → 발열 → 탄화 확정
- **설계 변경**: 산업용(IEC 60947-2) 또는 150A급 교체 · D-13 DFMEA 정식 등록
- **검증**: 알파2호기 현장 고장 분석 (C-114) → 원인 확정 (C-120)

#### A-2. LCD/RC/ADT 제어권 상태머신 버그 — Issue #79
- **고장모드**: FM-DM (제어권 전환 시 이전 속도지령 잔존)
- **근본원인**: NONE 상태가 모호한 전환 허용 · 모드 진입 시 Init 루틴 누락
- **설계 변경**: NONE 상태 삭제 · 모든 Transition에 Init(속도 0) 루틴 강제 · 3모드 간소화
- **검증**: 재현 시험 → 무인 전진 0건 · 안전 검증 통과

#### A-3. 펌프 동파 — 솔레노이드 오링 설계 변경
- **고장모드**: 밸브 밀폐 불량 → 잔수 → 동파 (5호기 동시 발생)
- **근본원인**: 오링 가공불량 (depth + wall thickness 규격 미달)
- **설계 변경**: 오링 20개 재발주 + **설계 규격 재정의** (depth/wall thickness)
- **검증**: 동일 조건 재현 시험 → 재발 0

#### A-4. GND 바운스 + P-15 노이즈 대책
- **고장모드**: FM-6 (GND 바운스 노이즈) · PFMEA P-15 노이즈 경로
- **근본원인**: 쉴드/접지 경로 미완 (현장 실측 확인)
- **설계 변경**: SYS FM-4, FM-6 DFMEA 반영 · 쉴드·접지 대책 현장 적용
- **검증**: 현장 실측 확인 (C-122)

**CAN — 단일 노드에서 5노드 분산 시스템으로**

> 통신이 깨지면 제품이 죽는다. Breaking Change 4건을 사전에 잡아낸 것은 체크리스트가 있었기 때문이다.

### 7A.2 주요 활동
- **5노드 토폴로지 설계**: VCU ↔ 구동×2 ↔ 팬 ↔ 펌프 ↔ BMS
- **DBC 4종 직접 작성/관리**: CAN ICD V03, BMS ICD V03 (C-13/C-15/C-38/C-39)
- **CAN BusLoad 분석**: 부하율 수치 검증 (C-17)
- **DBC 버전 비교 — BREAKING CHANGE 4건 검출**: 250317 vs 251125, 신규 4메시지 (C-49)
- **CAN 정합성 체크리스트 3차 반복** — 검증 프로토콜 표준화
- **EOP 시기 CAN Sleep/Wakeup 구현**: MC9S12ZVMC, 5차 rev, 암전류 요구 충족

## 7D. 공통 메시지 (Track A/B/C/D/E 하단 앵커)
> 5개 Track이 각각 다른 분야지만, **접근 방식은 같다**:
>
> 1. **현상**을 의심하지 않고, **원인**을 추적한다 (DFMEA)
> 2. **가설**을 세우고, **시험**으로 증명한다 (기획 → 설계 → 증명 → 분석)
> 3. **대책**은 설계 변경까지 간다 (양산 체계에 반영)
> 4. **제품 생애주기**를 따라간다 (차세대 기획까지)
> 5. **분야 경계**를 넘는다 (전력제어 담당이라도 기구/FW/재료 넘나듦)

## 7. 시험 — 기획·설계·증명·분석

### 7.1 섹션 타이틀
**시험으로 증명한다 — 기획/설계/증명/분석**

> 시험은 몇 개 만들었는가가 중요한 게 아니다.
> **매번 어떻게 접근하는가**가 역량이다.

### 7.2 4단계 프로세스

#### 1. 기획 (Plan)
**어떤 가설을 세우는가?**
- EOP: "SVPWM 절환이 FET 온도를 낮추는가?"
- SS500 범퍼: "3km/h 주행 중 장애물 접촉 시 정지거리는?"
- SS500 팬: "프로펠러 직경 변경이 풍속에 미치는 영향은?"

#### 2. 설계 (Design)
**장비가 없으면 만든다**
- 다이나모미터 토크제어 시스템 — 비선형성 0.008% 달성
- 팬 벤치 / 펌프 벤치 / 범퍼 시험대 직접 구축
- CAN 정합성 체크리스트 — 반복 검증 프로토콜 표준화

#### 3. 증명 (Prove)
**데이터로 답한다**
- FET 온도 1~6°C 저감 (2,932 데이터 포인트, PWM 온도 비교)
- 풍속 +57% (7.9 → 12.4 m/s, 20파이 프로펠러 채택 근거)
- 정지거리 0.082m, 피크 308A (자율주행 안전 확보)
- 극저온 기동 300초 → 100초 (-40°C 실증)

#### 4. 분석 (Analyze)
**데이터가 말하는 것 → 다음 결정**
- SVPWM 채택 결정 근거 제공 → 국책과제 완료
- 펌프 업그레이드 보류 (비용 3배 + 운전시간 반감 트레이드오프)
- 팬 20파이 프로펠러 채택 (+57% 정량 비교)
- 오링 설계 변경 (규격 재정의 후 재발 0)

### 7.3 섹션 하단 메시지
> 대학원에서 Ansys Maxwell → MATLAB/Simulink → 실험 검증으로 훈련된
> "**모델 → 시뮬레이션 → 실험**" 체질이, 실무의 "기획 → 설계 → 증명 → 분석"으로 이어진다.

- **Obsidian 지식관리** — SS500 프로젝트 297노트 온톨로지
- **야간 무인 실행** — cron 00:00 → tonight_prompt → 아침 브리핑

### 8.3 왜 두 가지 축인가 (철학, 담담한 톤)

**1) 공학적 문제 해결 마인드**
공학적으로 문제를 파악·분석·해결한다.
시험과 데이터로 증명한다.

**2) 사람의 편리함을 제공하는 마인드**
소비자 니즈를 읽고 분석한다.
해결책을 제시한다.

**왜 두 개를 같이 하는가.**

자동화의 끝에는 인간이 직접 하고 있는 1차 산업과 노동이 남는다.
그 노동을 해결하는 기업이 진짜 리더가 될 것이다.

농업 자율주행(SS500)은 그 시작점이다.
AI 워크플로우는 그 자동화의 공학적 훈련이다.

두 축이 만나는 지점에서 나는 일한다.
